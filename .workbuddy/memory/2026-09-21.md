# 2026-09-21 工作日志

## 修复：「编辑 SQL → 重新执行」后数据没被呈现（用户反馈）

### 现象
用户把「最近 7 天」的 SQL 改成 30 天后点「重新执行」，toast 显示成功、思考过程里的摘要也变了，
但界面上看不到任何新数值，以为没生效。

### 根因（不是执行失败，而是结果没送到眼前）
用脚本直连 `/api/execute` 实测：7 天 → `null`，30 天 → `84365`，**后端一直在正确返回新数据**。
问题在前端呈现层，共三处断点：
1. `/api/execute` 的 `summary` 只写「共返回 N 行」，而对话区正文取的就是 summary
   （execute 不会产生 markdown 结论组件），所以数值根本没进对话区。
2. 「思考过程 → 模型输出」区块渲染的是 `turn.stream`（LLM 原始流），重新执行走 `/api/execute`
   不产生新流，这块永远显示最初的 7 天 SQL，视觉上极像「没生效」。
3. 重新执行后停留在「SQL 语句」页签，不自动切到「查询结果」，表格数据在另一个页签里。

### 改动
- `lib/result-builder.ts`：新增 `buildRowsSummary()`。单行结果（SUM/COUNT）直接把字段值写进摘要
  （带千分位、空值显示「无数据」），多行给「N 行 + 首行预览」，零行给明确提示。
- `app/api/execute/route.ts`：`summary` 改用 `buildRowsSummary`。
- `app/page.tsx`：重新执行成功后 `setTab('overview')` + `setPanelDismissed(false)`，
  并给 turn 打 `rerunAt` 时间戳；toast 文案改成带数值的摘要。
- `app/components/types.ts`：`Turn` 增加 `rerunAt?: number`。
- `app/components/ChatPanel.tsx`：思考过程 header 加「已重新执行」徽标；模型输出下方加一行说明，
  明确「这块是模型首次生成的原始输出，重新执行不改写它」。

### 顺手修的 bug
`lib/error-hints.ts` 的 permission 规则里正则写死小写 `仅允许 select`，而 validator 的实际文案是
`仅允许 SELECT 查询（...）`，没加 `i` 标志 → DELETE 这类写操作被归到 unknown 兜底，
对用户显示成「执行失败」而不是「安全拦截」。已加 `i` 标志并补回归用例。

### 3) CR 发现的隐藏问题 + 已修复
- **【高·已修】日期整体偏移一天 + 图表 X 轴英文长日期**：`pg` 默认把 `date/timestamp` 解析成 `Date` 对象，
  JSON 序列化后变 UTC ISO（`2026-09-12 +08:00` → `"2026-09-11T16:00:00.000Z"`），表格/导出日期全错一天。
  修法：`lib/db.ts` 用 `pgTypes.setTypeParser(1082/1114/1184, v=>v)` 让日期以字符串 `YYYY-MM-DD` 返回。
- **【中·已修】`isNumericColumn` 把日期列误判成数值列**：`parseFloat('2026-09-12')=2026` 导致图表选错轴。
  改严格数值正则 `/^-?[\d,]+(\.\d+)?$/` 排除日期/时间字符串。`buildEchartsComponent` 的 date 维度现在正确当类别列。
- **【中·已修】安全校验漏掉 `SELECT INTO` 建表**：只读校验只拦 INSERT/UPDATE/...，漏了 `SELECT ... INTO` 新建表。
  已在 `validateSQL` 加 `\binto\b` 拦截（返回「禁止创建新表」）。
- **【低·已修】强制 LIMIT 被结尾注释吞掉**：`SELECT ... -- 备注` 追加上去的 `LIMIT` 落在注释里失效。
  已先 `replace(/--[^\n]*$/, '')` 再追加 LIMIT。
- **【低·已修】SQL 缓存 LRU 触达不刷新 `at`**：热 key 仍按首次写入时间过期。已在触达时 `entry.at = Date.now()`。

## 需求：生产环境每日大模型调用上限 5 次 + 输入输出上下文限制（简历/公网场景）

### 为什么是「落库计数」而不是内存 Map
Netlify serverless 每次调用进程独立、内存不跨实例共享；用 `Map`/`sql-cache` 那种进程内计数，
冷启动就归零，限流形同虚设。故新增 `t_rate_limit` 表 + 原子「条件自增」。
并发超发防护：`INSERT ... ON CONFLICT (quota_date) DO UPDATE SET used_count = used_count + 1 WHERE used_count < $limit`
（达上限时 UPDATE 被 WHERE 过滤、0 行 → 拒绝且不超发）。

### 改动
- **新增 `lib/rate-limit.ts`**：
  - `isRateLimitEnabled()`：默认仅 `NODE_ENV==='production'`；`RATE_LIMIT_ENABLED` 可强制开/关。
  - `consumeDailyQuota()`：原子条件自增，返回 `allowed/used/limit/remaining/resetAt/retryAfterSec`；DB 异常抛出（调用方降级放行）。
  - `getDailyUsage()`：只查不消耗，供状态展示。
  - 按**北京时间自然日**计日（`Intl` Asia/Shanghai + 次日本京 00:00 算 `Retry-After`）。
  - `ensureTable()`：`CREATE TABLE IF NOT EXISTS t_rate_limit`，进程内只建一次（失败自愈）。
  - 配额 `LLM_DAILY_LIMIT`（默认 5），可环境变量覆盖。
- **`app/api/chat/route.ts`**：
  - 顶部算 `cacheKey`/`cached`；`isRateLimitEnabled() && !cached` 才 `consumeDailyQuota()`；
    配额耗尽 → 返回 **HTTP 429 + `Retry-After` 头 + JSON 友好文案**（前端 `ask` 现读取 `body.error` 展示）。
  - 命中 SQL 缓存的请求跳过 LLM，不计配额（符合「只统计真调大模型」）。
  - 输入上下文限制：`MAX_QUESTION_LEN`（默认 1000）超限 → 400 拒绝。
  - 输出上下文限制：`ChatOpenAI` 加 `maxTokens: MAX_TOKENS`（默认 2048）。
  - `/api/execute` 重跑 SQL 不走模型、不计数（保持原样）。
- **`app/page.tsx`**：`ask` 的 `!response.ok` 分支改读响应体 `error` 字段，429/400 显示服务端友好文案而非裸「服务返回 429」。
- **`test-data/schema.sql`**：追加 `t_rate_limit`（`IF NOT EXISTS` + **不带 DROP**），避免 `seed:db` 重建 5 张业务表时把计数清掉；该表不入 `ALLOWED_TABLES`，只由 `lib/rate-limit.ts` 直连读写。
- **`lib/db.ts`**：`query` 形参 `params?: []` 改 `params?: unknown[]`（原空元组类型过严，导致带参查询类型报错）。
- **新增 `lib/__tests__/rate-limit.test.ts`**：6 条覆盖 `isRateLimitEnabled`（env 组合）+ `beijingDateStr`（跨 UTC 日界归北京自然日）。

### 上下文限制建议（已落地的取舍，供简历讲解）
- **输入**：问题长度上限（防超长 prompt 滥用/控成本）+ 历史已限最后 4 条 + 候选项检索 TopN + few-shot 固定 9 例。
  对公网功能这三道已够；若要更严可再限 `messages` 总 token。
- **输出**：`maxTokens` 上限（JSON 输出 2048 足够）；避免模型无限吐 JSON 拖垮延迟与成本。
- 这两类是「成本/滥用/DoS 防护」的刚需，**只在生产生效**（本地开发不挡），便于自测。
