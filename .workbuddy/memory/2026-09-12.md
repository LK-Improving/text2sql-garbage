### 🔴 头号发现：表结构注入实质失效（FR2 名存实亡）
- `lib/table-metadata.ts` 导出的是**模板字符串**，而 `app/api/chat/route.ts:201` 写 `Object.values(TABLE_METADATA)`
  → 对字符串调用得到**字符数组**（实测 40 个单字符：`["1","."," ","表","名",...]`），
  再 `JSON.stringify` 后当作表结构注进 prompt。
- 一直没暴露的原因：Few-Shot 示例里恰好带了表名/JOIN/`region_name`，模型靠示例硬扛；
  问到 `t_weigh_bill` / `t_alert` 这类示例未覆盖的表必然幻列。
- **附带隐患**：`lib/schema.ts` 与 `lib/table-metadata.ts` **同时导出同名 `TABLE_METADATA` 但类型完全不同**
  （前者结构化对象、缺 t_weigh_bill；后者字符串、5 张表）。这是两处各自演化的根源。
- 结论：确立**单一数据源 = `lib/schema.ts`**，删掉字符串版本。

### 🔴 `lib/validator.ts` 与 FR3 要求差距大（只有 16 行）
`;` 被列为禁用词（会误伤字符串字面量与单语句结尾分号）；`includes('DELETE')` 子串匹配会误杀
`WHERE remark='DELETE'`；**无表名白名单**（FR3 明确要求，也是面试考点）；无系统表/危险函数拦截
（`pg_read_file`/`pg_sleep`/`COPY`/`information_schema`）；无多语句断言；`LIMIT` 判断同为 `includes` 会漏加；无查询超时。

### 🔴 评测集从未跑过
`test-data/text2sql-eval.jsonl` 32 条已就绪（区域趋势4/车辆排行4/预警明细5/边界陷阱4/安全拒绝3/
时间聚合3/车辆明细3/综合查询2/磅单2/状态聚合1/区域明细1），但**无任何执行脚本**，

## P0 三项已全部落地（含前后对照）

### P0-1 表结构单一数据源
- 删除 `lib/table-metadata.ts`（字符串版）；`lib/schema.ts` 重写为结构化定义，
  **严格对齐 information_schema 实际列**（5 表；删掉了库里不存在的 `t_alert.severity`、
  `t_vehicle.vehicle_type`，补上了 `t_weigh_bill`）。
- 新增 `renderTableInfo()`（表结构 + JOIN 关系 + 5 条口径提醒），route.ts 改为 `renderTableInfo()` 注入；
  db.ts 加 `pool.on('connect')` 设置 `statement_timeout='10s'` + `max:10`。
- 字段 description 里写清单位/取值（如"总清运量单位 kg"、"车牌可能带间隔点·"），这是模型选列的关键。

### P0-2 validator 重写（lib/validator.ts）
- 先 `stripLiteralsAndComments()` 剥离字符串字面量与注释，再做词法级匹配（不再 `includes('DELETE')`）。
- 7 道关卡：单语句 → 必须 SELECT/WITH 开头 → 写操作关键字 → 危险函数/系统表
  （pg_read_file/pg_sleep/COPY/information_schema/pg_authid…）→ **表名白名单**（ALLOWED_TABLES）
  → 强制 LIMIT（无则补 1000，>10000 收敛）。
- CTE 名/派生表别名要排除：收集 `AS x` + `) x` + `WITH x AS (` 三处来源。
- 冒烟测试 23 条全过（字面量里的 DELETE、注释里的注入、REPLACE 只读函数、CTE、派生表、schema 前缀均放行）。

### P0-3 评测脚本 `text2sql-garbage/scripts/run-eval.mjs`
- 调 /api/chat 拿 SQL → 用 pg 分别执行「生成 SQL」和「标准答案」→ 比对结果集 → 出 md + json 报告。
- 判定：match / match_extra（期望列对但多给列，算通过）/ partial（列顺序或别名不同）/ mismatch /
  exec_error / false_reject / false_accept。
- **判定口径的关键决定**：容忍「多给列」。评测集自带 `expected_columns`，设计意图是校验关键列，
  不是要求 SELECT 列表逐字一致。改口径后准确率 41.4% → 62.1%。

## 本轮踩坑
1. **`\b(?:with|,)` 的 `\b` 对逗号不成立** —— `),` 两侧都不是单词字符，导致第 2 个及之后的 CTE 全漏抓，
   `month_alert`/`ranked` 被当成真实表误拦。改成 `(?:\bwith|,)`。
2. **改 `lib/` 下的服务端代码后 `next dev` 不会热更新**，必须 kill 后重启，否则评测跑的是旧代码（白跑两轮）。
3. 评测比对要处理**列顺序**：`Object.values` 按 SELECT 顺序，生成 SQL 与标准答案列序不同会假 mismatch；
   宽松比对要把每行内的值也排序。
4. **`lib/`、`app/api/`、`app/components/`、`scripts/` 全部未纳入 git**（只有脚手架文件是 tracked）。
   做不了 `git stash` 对照，本轮是手工还原旧代码跑的；**强烈建议尽快 commit 一次**。
5. 报告文件名用 `toISOString()` 会落到 UTC 日期（本地 9/12 生成却显示 20260911），已改为本地时间。
